# Decisions

Decisions about the engineering standard itself, recorded so they aren't argued again (constitution I and Amendments). Newest first; a reversal is a new entry that names the one it replaces.

Entries 1 to 6 record decisions the Owner and Planner made on 2026-10-07, before this repository existed. They were entered that day from `BRIEF-01-build-standard-repo.md`, `CONSTITUTION.md` v0.1, and `STANDARD.md` v0.1, and their dates and rejected alternatives were completed on 2026-10-08 from the Planner's record (brief 02).

## 17. Agents cannot reliably edit permission files inside `templates/`; the Owner applies such edits

- **Date:** 2026-10-09
- **Decision:** The Owner applies edits to permission files inside `templates/` (the template's `.claude/settings.json`), in a terminal outside an agent session, and stages them. A Builder that is refused an edit to such a file stops and reports; it does not route around the refusal with another tool.
- **Rationale:** The permission system may refuse an agent's edit to a file that bounds agents, and a Builder that finds another route to it has defeated the boundary the Owner set. The workflow follows brief 07's behaviour: stop, report, and let the Owner decide. The detail stays in the untracked `.recon/brief-07/`.
- **Alternatives rejected:** working around a refusal with a shell edit, `Write`, or `git restore` (rejected: a refusal is the boundary working, not an obstacle).
- **What is verified:** the workflow was applied in brief 09: the Owner anchored four template deny rules and staged them before the Builder ran, and the Builder edited no settings file.

## 16. External process layers: depend on neither, and pin four skills (brief 08)

- **Date:** 2026-10-09
- **Decision:** (R1) foodplan runs on this standard's loop: Planner, Builder, Critic, one brief per session, evidence on disk, the gate. Spec Kit is not adopted. (R2) This repository depends on neither agent-skills nor Spec Kit; an adopter copies four agent-skills skills into a project at a pinned commit, under `templates/docs/SKILLS.md` (STANDARD 5.6). (R3) What is ours alone stays: walls, role separation, evidence, findings with IDs, hand-off, stack rules, supply-chain settings, environment findings. (R4) Nothing is deleted for being externally redundant. (R5) This repository stays "loop + walls", not a thin repository that depends on a process layer.
- **Rationale:** Spec Kit's unit and stop points do not match this loop, it adds a second principles file and a second spec location, and its only code-enforced gate exists under `specify workflow run`, not on the default path. The agent-skills plugin entry has no `ref` or `sha`, so its content cannot be pinned from outside; this repository carries the policy and the pin, not their text. The Planner's expectation that we would delete more than we keep is not borne out: about 4.8 KB, 1.1% of the four documents, is externally redundant. The real redundancy is inside this repository, where the same claim is kept true in 3 to 7 places.
- **Alternatives rejected:** a thin repository that depends on an external process layer (rejected: the walls and role separation exist in neither source, and an unpinned dependency lets its text change under the standard); Spec Kit (rejected: above); depending on the agent-skills plugin (rejected: its entry cannot be pinned); `/build auto` (rejected: it runs a whole plan in one session with no stop points).
- **The case against this decision (`.recon/brief-08/EVALUATION.md` §8):** this repository has one local commit, no remote, and no second reviewer, beside two projects that have both, and a copy pinned at a commit stops receiving their fixes unless someone diffs. Its walls are its least proven part: the ruleset and CI have never run on a real remote, and a hook that cannot start does not block (STANDARD 3.7).
- **What is verified:** `.recon/brief-08/EVALUATION.md`, measured against clones of both sources and spot-checked by the Planner. Always-on bytes: agent-skills 10,995, Spec Kit 1,299, this standard 924. Neither source has a wall on its default path. The four skills' names, sizes, and licence line at the pin are in `.recon/brief-09/skills-pin-check.txt`.
- **Revisit when:** agent-skills' plugin entry gains a `ref` or `sha`; either source ships a wall on its default path; or at v0.2.

## 15. Context and cost are part of the standard

- **Date:** 2026-10-08 (Owner request)
- **Decision:** STANDARD §10 sets rules for what a session costs: one brief per session, sized to finish under about 150k tokens (10.1); early compaction, with `"autoCompactWindow": 200000` in the template's `.claude/settings.json` (10.2); long output to evidence files that start with a result line (10.3); narrow reads (10.4); one docs cache, `.recon/docs/` (10.5); a model and effort named in each brief (10.6); only the connectors, servers, skills, and plugins a project uses, with `"disableClaudeAiConnectors": true` in the template for what a project can set (10.7); and subagents for broad research (10.8). All are [practice] or [checked]; none is a wall. The template's `AGENTS.md` gets a six-line "Working efficiently" section, `/eng-standard:gate` starts its evidence file with a `# result:` line, and `/eng-standard:handoff` keeps `docs/PROGRESS.md` under about 60 lines.
- **What is verified:** `autoCompactWindow` takes 100000 to 1000000 in any settings file and is capped at the model's window; unset, a model with a 1M window compacts at about 967K tokens. `/autocompact` saves a per-model window under `modelSettings` that wins over the key in the same file, `--autocompact` wins over the key for one launch, and `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, which takes a plain integer only, wins over all three (`.recon/brief-05/docs-excerpts.txt`, section A: `docs-cc-settings-reference.md` 2774 to 2790, `docs-cc-env-vars.md` 216, `docs-cc-model-config.md` 784 to 794). `disableClaudeAiConnectors` is valid in any settings file and a `true` in any of them applies, but only to the connectors Claude Code fetches itself (terminal, VS Code, JetBrains, and Agent SDK sessions). The desktop app delivers connectors in-process as `type: "sdk"` servers that no MCP setting reaches, `syncClaudeAiSkills` and `syncClaudeAiPlugins` are valid only in user, local, and managed settings, and `enabledMcpjsonServers` and `disabledMcpjsonServers` cover only servers a project's `.mcp.json` defines (section D: `docs-cc-mcp.md` 252, 316, 1173 to 1180, 1193; `docs-cc-desktop.md` 855; `docs-cc-settings-reference.md` 4268). Tool search defers MCP tool definitions by default (`docs-cc-mcp.md` 1479). Hook input: the fields every event shares (`session_id`, `transcript_path`, `cwd`, `permission_mode`, `effort`, and the rest) carry no context size, and `context_tokens` appears only on `PreModelSwitch` and on `SessionStart` for a resumed or forked session; `PreCompact` and `PostCompact` give `trigger` only (section E: `docs-cc-hooks.md` 724 to 737, 1144, 3110, 3136, 3247).
- **Rationale:** On 2026-10-08 most sessions ran past 150k tokens of context: a Planner session reached 322k and a Builder session 220k. Each session starts at about 57k tokens of tool definitions (Claude Code's tools about 31k, connector tools about 17k, skills about 6k) before any work, and every turn re-sends the whole conversation. The Owner is on the Pro plan, so this decides how much work fits in a week. The Owner's machine already sets `autoCompactWindow: 200000` in `~/.claude/settings.json`; the template carries the same value so every project starts with it.
- **Alternatives rejected:** leave it to habit (rejected: sessions reached 320k within a day); a hook that stops a session at a token count (rejected: no hook input on the events that run during a session exposes the context size, so a hook could only estimate it from the transcript file, which can lag the conversation, and stopping mid-step loses work, while compaction and brief sizing do the job).

## 14. The Supabase CLI runs outside the sandbox only by its absolute path; the local stack is a known exception

- **Date:** 2026-10-08
- **Decision:** Projects install the Supabase CLI outside the project, with Homebrew or a release binary checked against the release's checksums, never as a project dependency. The template's `sandbox.excludedCommands` names it by absolute path, `/opt/homebrew/bin/supabase` (Homebrew on Apple Silicon), for the local-stack commands only: `start`, `stop`, `status`, and `db reset`, `db diff`, `test db`, and `gen types` with `--local`. A machine whose CLI lives elsewhere adds its own path in `.claude/settings.local.json`. CI pins the CLI version with `supabase/setup-cli`'s `version` input. Projects without Edge Functions set `[edge_runtime] enabled = false` in `supabase/config.toml`. STANDARD 3.3 tags the exception: the local stack runs agent-written SQL (migrations, seed) and Edge Functions in Docker, outside the sandbox and its network allowlist.
- **What is verified:** Claude Code matches `excludedCommands` entries against the text of the call, so `/usr/local/bin/docker` doesn't match `docker *` and, the other way round, a bare `supabase start` doesn't match `/opt/homebrew/bin/supabase start *`; entries from every settings scope combine into one list (`.recon/brief-04/docs-cc-sandboxing.md`, "Run commands outside the sandbox with excludedCommands"; `docs-cc-settings-reference.md`, `sandbox.excludedCommands`). A leading assignment such as `PATH=… /opt/homebrew/bin/supabase start` keeps the call sandboxed: in Claude Code 2.1.293 the matcher strips only assignments of a fixed list of harmless variables (`NODE_ENV`, `LANG`, `TZ`, and others; not `PATH`), and a call that still starts with an assignment isn't covered (`cc-binary-shell-mode-and-excluded-commands.txt`, functions `zbr`, `man`, `f9`, and the list `UW`). `setup-cli`'s `version` input takes "a fixed version published to npm" (`.recon/brief-01/action-yml-supabase-setup-cli-v3.0.1.yml`). `[edge_runtime] enabled` is a key of the CLI v2.120.0 config, and `start` starts the Edge Runtime container only when it is true (`.recon/brief-04/supabase-cli-v2.120.0/`).
- **Rationale:** `pnpm exec supabase …` ran the binary from `node_modules/`, which sandboxed commands can rewrite, outside the sandbox (Critic v0.1.0 pass 2, R2-3). An absolute path outside the project names one binary that agents can't change. The local stack needs Docker, which can't run in the sandbox, so its exception is written down rather than hidden.
- **Alternatives rejected:** keep `pnpm exec supabase` (rejected: R2-3); bare `supabase …` entries (rejected: resolved through `PATH`, which a command can change); have the Owner start the stack outside Claude Code and let agents only connect (rejected for now: the Builder resets the database after each migration; recorded as the fallback if the exception proves too wide).

## 13. Guard checks run from the base branch

- **Date:** 2026-10-08
- **Decision:** On pull requests, the guard checks (Migrations are append-only, Test integrity, Sensitive change, Actions pinned to commit SHAs, Secret scan, and Release age) run in `guards.yml` on `pull_request_target`. GitHub takes that workflow from the default branch, and each job checks out the default branch without stored credentials, fetches the pull request head as git data only (`refs/pull/<number>/head`), and runs the default branch's copies of the scripts against `<base>...<head>`. Nothing from the pull request is installed, built, or run, no pull-request value reaches a `run:` line except through `env:`, and the token is read-only. `ci.yml` keeps the jobs that must run the pull request's code (Gate, Dependency audit) and, on a push to `main`, runs the secret scan, the pinning check, and the migration check again under names that differ from the required checks, so a job skipped on a pull request can't satisfy one. The pull request that first adds `guards.yml` isn't judged by it; the Owner merges that one with the override.
- **What is verified:** GitHub's docs: `pull_request_target` "runs in the context of the default branch of the base repository", and `actions/checkout` without a `ref` takes the default branch; checks from `pull_request_target` runs count for required status checks; a job skipped by a condition reports success (`.recon/brief-04/docs-gh-events.md`, `docs-gh-securely-using-pull-request-target.md`, `docs-gh-troubleshooting-required-status-checks.md`). The demo in a throwaway repository: a pull request that edits a shipped migration, `package.json` scripts, and both check scripts passes its own copies and fails the base copies run as `guards.yml` runs them (`guards-demo.txt`).
- **Known limit:** a pull request can add a job to `ci.yml` with the same name as a guard check. GitHub's docs say only that a job name used in more than one workflow "can cause ambiguous status check results"; how a required check resolves two runs with one name wasn't verified. Sensitive change still fails on that pull request, and the Owner reads the checks list and what a push carries before pushing (`docs/ADOPTING.md`).
- **Rationale:** On `pull_request`, GitHub runs the workflow and scripts from the pull request's own merge commit, so a pull request could change or skip the check that would flag it (Critic v0.1.0 pass 2, R2-2).
- **Alternatives rejected:** keep the guards in `ci.yml` (rejected: R2-2); run the pull request's code under `pull_request_target` (rejected: the "pwn request" pattern GitHub warns about, with a write-capable context).

## 12. Agents can't reach GitHub; the Owner pushes

- **Date:** 2026-10-08 (Owner decision)
- **Decision:** Agent sessions have no route to GitHub at all. The Owner pushes, opens pull requests, and merges; agents commit only with the Owner's approval. The template's sandbox allowlist holds only `registry.npmjs.org`; `git push` is a deny rule, and commit-hygiene blocks it in every form it can read ("The Owner pushes (STANDARD 1.6)"). On the Owner's machine, `~/.claude/settings.json` sets `sandbox.network.strictAllowlist: true` together with the machine's own `allowedDomains`, because with the lock on Claude Code ignores a repository's `allowedDomains`; the lock and that list apply to every project on the machine that has the sandbox on, and a project that needs another host has the Owner add it there. `main` has a ruleset: a pull request is required, with the required checks from GitHub Actions, force pushes are blocked, deletions are restricted, and the repository admin role may bypass only through a pull request, so nobody pushes to `main` directly. The Owner pushes with `!` commands in the session or from a terminal. Claude's file tools don't go through the sandbox, and in auto mode a write to `.git` goes to the permission classifier rather than being denied, so the template and this repository also deny `Edit` on `.git/config`, `.git/config.worktree`, and `.git/hooks/**` (`Edit(/.git/config)`, `Edit(/.git/config.worktree)`, `Edit(/.git/hooks/**)`): the Owner's `!git push` and terminal git run unsandboxed and read `.git/config`, so a `core.hooksPath`, `core.fsmonitor`, or `core.sshCommand` written there would run with the Owner's credentials (STANDARD 1.6, 3.5; `.recon/brief-04/docs-cc-permission-modes.md`, "Protected paths"; `.recon/brief-05/git-config-deny.txt`; `.recon/brief-06/git-deny-wide.txt`). The rules anchor at the session's primary working directory, so in a linked git worktree, where the project's `.git` is a file and the shared `.git` sits outside them, only the protected-path handling applies, which in auto mode routes a write to the classifier rather than denying it (`.recon/brief-04/docs-cc-permissions.md:374`). v0.1.0 supports local sessions only.
- **What is verified:** `strictAllowlist` is read only from user settings, managed settings, and `--settings` (a repository can't turn it on or off), needs Claude Code v2.1.219 or later, and from v2.1.285 makes Claude Code ignore a repository's `allowedDomains`, its `WebFetch(domain:...)` allow rules, and its proxy ports; with it on, the sandbox proxy refuses an unlisted host in every permission mode (`.recon/brief-04/docs-cc-settings-reference.md`, `docs-cc-sandboxing.md`). Code sessions in the desktop app share `~/.claude/settings.json` with the CLI (`docs-cc-desktop.md`, "Shared configuration"). Commands typed at `!` run outside the sandbox, and in Claude Code 2.1.293 they call the Bash tool directly, past the permission check and the PreToolUse hooks, so neither a deny rule nor a hook blocks the Owner's push (`docs-cc-interactive-mode.md`; `cc-binary-shell-mode-and-excluded-commands.txt`, function `V` and `Hy`). In a ruleset the repository admin can bypass only when on the bypass list, and "For pull requests only" makes the bypass go through a pull request (`docs-gh-creating-rulesets.md`, `docs-gh-available-rules-for-rulesets.md`); rulesets are available for private repositories on GitHub Pro (`docs-gh-availability-extracts.txt`). Pull request authors can't approve their own pull requests, so the solo Owner's ruleset requires 0 approvals (`docs-gh-approving-a-pull-request-with-required-reviews.md`). Cloud sessions don't install the plugins a repository declares, and reach GitHub through a proxy that attaches the Owner's credentials, so neither the guardrails nor this wall holds there (`docs-cc-cloud-environments.md`, "What carries over from your setup" and "GitHub proxy"). `Read` and `Edit` deny rules are merged into the final sandbox configuration and block access there too (`docs-cc-sandboxing.md:650`, `:655`, `:263`), so a rule covering all of `.git` makes `.git/index.lock`, `.git/index`, and `.git/objects/**` unwritable to every sandboxed command and an agent session can no longer stage or commit; brief 06's `Edit(/.git/**)` did exactly that (`.recon/brief-06/git-deny-wide.txt`), and with the three narrow rules back `git add` and `git rm --cached` work again in the same session (`.recon/brief-07/settings-revert.txt`). That is why the rule covers only paths git never writes during ordinary work. Whether `Edit(/.git)` on its own, which would also cover a worktree's `.git` pointer file, is safe was not probed (`.recon/brief-07/git-entry-probe.txt`), so it is not in the rule set. What stays uncovered: `.git/modules/**/config` and `.git/modules/**/hooks/**` in a project with submodules, `.git/worktrees/**/config.worktree`, and the worktree pointer file, none of which the standard's workflow produces, because sessions run at the repository root.
- **Rationale:** An agent's `git push` carried the Owner's admin credential, so the guardrails were all that stood between an agent and `main` (Critic v0.1.0 pass 2, R2-1).
- **Alternatives rejected:** a separate GitHub account for agents (rejected: a second account to manage, and the Owner's credential sits on the same machine, so it's hard to make airtight); keep the `git push` ask rule (rejected: a guardrail only, and the push carries admin rights; R2-1).

## 11. Guardrails and walls

- **Date:** 2026-10-08
- **Decision:** `STANDARD.md` tags a rule **[enforced]** only when a wall holds it: something that holds against a determined agent, such as the OS sandbox (files and network), GitHub-side controls (a ruleset on `main`, required checks), CI checks on committed content that run from the base branch, database constraints and policies, and the Owner's review at merge. Hooks and permission rules that read commands or paths are guardrails, tagged **[guarded]**, and a [guarded] rule names the wall behind it. Every protection that matters gets a wall. The walls in v0.1.0:
  - the sandbox's network allowlist, which gives agent sessions no route to GitHub (entry 12), with `strictAllowlist` on the Owner's machine;
  - the sandbox's write block on `.github/`, `.githooks/`, the gitleaks files, and `.env*` files;
  - the ruleset on `main`, whose only bypass is the Owner's, through a pull request;
  - the CI checks Migrations are append-only, Test integrity, Sensitive change, Actions pinned to commit SHAs, Secret scan (gitleaks's built-in rules, ignoring a repository's `.gitleaks.toml`), and Release age, which run from the base branch on pull requests (entry 13), and row-level security in the Gate;
  - the Owner's checks at adoption and at each phase gate, tagged [checked]: no real secret in a project's `.env*` or key files on a machine where agents run (STANDARD 3.1, entry 7), no production credentials on development machines (3.8), and no privileged key in the app's hosting environment (4.2, with the client bundle check as a CI backstop).
- **Rationale:** The Critic pass on v0.1.0 (`.recon/critic-v0.1.0/REPORT.md`, CR-4) found spellings git accepts that the commit-hygiene hook missed, and Claude Code's permissions docs say a Bash deny rule "isn't a security boundary around the program". A rule called enforced that a guardrail alone holds overstates the protection (constitution XII). Guardrails still stop most real mistakes early and cheaply, before a wall has to.
- **Alternatives rejected:** keep calling hooks "enforced" (rejected: overstates protection, constitution XII); remove the hooks (rejected: they stop most real mistakes early).

## 10. The stop gate asks for a passing fast gate; it runs nothing itself

- **Date:** 2026-10-08
- **Decision:** The stop-gate hook never runs the project's scripts. The `/eng-standard:gate` skill runs `gate:fast` (`/eng-standard:gate fast`) or the full `gate` with Bash, inside the sandbox, and records the result in `.recon/gate/last.json` with a fingerprint of the uncommitted non-doc changes. When a Builder session is about to stop with such changes and there is no passing record for the current fingerprint, the hook blocks the stop once with "Run `/eng-standard:gate fast` before finishing; CI runs the full gate." Planner sessions, review agents, and sessions without a role record are never blocked. A project with no `gate:fast` script has no stop gate. The record isn't protected; a forged one only silences the reminder, and CI's required Gate check is the wall.
- **Replaces:** brief 01's design, in which the hook ran `gate:fast` itself whenever the working tree had uncommitted changes.
- **Rationale:** Hooks run outside the sandbox, so a hook that runs project scripts runs agent-editable code with the user's full access, and its output went back to Claude in the block reason (Critic v0.1.0, CR-1). Running the gate through Bash keeps it in the sandbox. Tying the check to the tree fingerprint and the Builder role means a read-only session, or a Builder that has already run the gate on the current changes, is never stopped (CR-14). CI runs the full gate as a required check before anything merges (STANDARD 2.1, 9.2).
- **Alternatives rejected:** run the full gate on every stop (rejected: integration tests need local Supabase running and take minutes; CI and `/eng-standard:gate` run the full gate); run `gate:fast` in the hook (rejected: unsandboxed, CR-1).

## 9. The Planner guard marks sessions by their first prompt

- **Date:** 2026-10-08
- **Decision:** A session's role is fixed by its first prompt. A session whose first prompt is sent in plan mode is a Planner session for the rest of its life, whatever the permission mode is later: Claude's file tools can't change files in the repository, and its Bash, PowerShell, and Monitor commands must be on the read-only allowlist the review agents use (read-only git, read-only file utilities, the test and typecheck scripts). Any other session is a Builder session, which plan mode alone governs, so a Builder can explore, plan, have the plan approved, and implement in one session. A resumed session keeps its role. A role record that exists but can't be read counts as a Planner, and no session's file tools may write the plugin's data directory, where the records live. Roles are removed 30 days after a session's last prompt. A Planner session is never forked to build (STANDARD 1.1). The guard is a guardrail; the Owner's review at merge and the protected `main` are the walls (entry 11).
- **Replaces:** brief 01's sticky plan-mode marking, in which any session seen in plan mode became read-only for the rest of its life (never released).
- **Rationale:** Planner and Builder are never the same session, and the Planner can't edit the repository (STANDARD 1.1, 1.2). The Owner starts a Planner in plan mode, so the first prompt identifies it without anyone keeping a list, while Builders keep the recommended explore, plan, implement flow. The shell allowlist and the fail-closed record close the routes the Critic found on 2026-10-08 (CR-7: writing files through Bash; CR-10: rewriting the role record).
- **Alternatives rejected:** sticky marking on any plan-mode use (rejected: locks out Builders that plan before implementing); a hand-maintained session-ID list (QuaSaR; rejected: a forgotten entry leaves a session unguarded).

## 8. Repository visibility and GitHub plan

- **Date:** 2026-10-08 (the ruleset updated the same day after the second Critic pass, R2-1)
- **Decision:** This repository is public. Consumer projects are private on GitHub Pro. `main` is protected by a ruleset, the only path `docs/ADOPTING.md` describes: a pull request is required, with 0 approvals; the status checks are required, each with GitHub Actions as its expected source; force pushes are blocked and deletions restricted; and the repository admin role is on the bypass list in "For pull requests only" mode, never "Always allow". A local gitleaks pre-commit hook stands in for push protection.
- **Rationale:** This repository holds no secrets, and as a public repository it can be added as a plugin marketplace on any machine without git credentials. GitHub Pro gives a private repository rulesets, so green CI is enforced before merge (STANDARD 9.1). A solo Owner can't approve their own pull request, so required approvals would block every merge; the Owner's review is the merge itself. With the admin bypass limited to pull requests, nobody pushes to `main` directly, the Owner included, and an override is a deliberate merge with a trail. Push protection for a private repository needs GitHub Secret Protection, which GitHub sells only for organization-owned repositories on Team or Enterprise, so each project scans staged changes locally, keeps the CI secret scan, and records the difference from STANDARD 4.6 in its `docs/DEVIATIONS.md` (`docs/ADOPTING.md`, GitHub settings).
- **Alternatives rejected:** stay on GitHub Free with a recorded deviation (rejected: without branch protection nothing enforces green CI before merge); keep this repository private (rejected: needs git-credential setup on every machine and a paid plan for its own branch protection, and it holds no secrets); a branch protection rule instead of a ruleset (rejected: on a repository owned by a personal account it can't put the admin on a bypass list limited to pull requests, so the admin could push straight to `main`; R2-1); require one approving review (rejected: the solo Owner can't approve their own pull request).

## 7. No real secret in an agent's working tree; the `.env*` read block is a guardrail

- **Date:** 2026-10-08 (corrected the same day after the Critic pass, CR-1 and CR-23, and after the second pass, R2-4)
- **Decision:** The wall is that there is nothing to read: on a machine where agents run, `.env*` and key files in a project hold only local, non-secret values (the local Supabase URL and keys, local ports), real secrets live only in the hosting provider, and production credentials stay off the machine (STANDARD 3.1, 3.8, 4.6). The Owner checks it at adoption and at each phase gate, and never runs `vercel env pull` on such a machine. The template still blocks `.env*` files as a guardrail: `Read(.env*)` and `Edit(.env*)` deny rules for Claude's file tools, and `sandbox.filesystem.denyRead` and `denyWrite` entries `./.env*` and `./**/.env*` for sandboxed commands, so they can't read, write, rename, copy, or link one at the project root or at any depth below it. Local development takes local Supabase values from `supabase status -o env`. Hooks run outside the sandbox, so no hook runs project code (entry 10).
- **What is verified:** the settings reference documents the entries' syntax (`./` resolves against the project root; `**/` matches any depth); a bare file name in a permission rule matches at any depth, so `Edit(.env*)` covers nested files. With the profile Claude Code 2.1.293 builds, taken from its own code and run with macOS's `sandbox-exec` (not inside a live session, which this machine can't run), every form inside the project was denied: reading the file, renaming it in place, copying it, a hard link, a symlink, moving its directory or the top-level directory within the project, `cp -R`, `tar`, and writing a new `.env*` file (`.recon/brief-04/sandbox-check.txt`). The sandbox's read block has a known bypass for shell commands. Reported to Anthropic through its disclosure programme on 2026-10-09. Not known to be fixed as of that date. The method stays out of this repository until a fix ships or 90 days pass (about 2027-01-07). On Linux and WSL2, Claude Code expands a wildcard read entry to the files that exist when the sandbox starts, and skips a write entry that contains a wildcard, so `./.env*` and `./**/.env*` don't stop a rename or a new file there. The check inside a real session is a required item of `docs/ADOPTING.md`'s "Check the adoption".
- **Rationale:** Agents cannot read secrets (constitution V). Whatever a command can read, it can print, and a command's output reaches the agent. A read block with a known gap is a guardrail; the only wall a determined agent can't get past is a secret that isn't on the machine.
- **Alternatives rejected:** let sandboxed commands read `.env.local` (rejected: a dev server or test run is a path for a secret to reach tool output); also deny `/**/.env*` everywhere on the machine, or close the known bypass with extra deny entries (tested, not applied: neither covers key files, the first walks the whole filesystem on Linux, and the second breaks whenever the sandbox's own paths change; `.recon/brief-04/sandbox-r2-4-candidates.txt`).

## 6. CI runs on a protected `main`

- **Date:** 2026-10-07
- **Decision:** `main` is protected: pull requests only, required CI checks, no force-push, no deletion. CI runs the full gate, the migration replay, the row-level security tests, secret scanning, the dependency audit, and the action-pinning check, and nothing merges without green CI.
- **Rationale:** Small, reversible steps; nothing merges without green CI (constitution XI; STANDARD 9.1, 9.2).
- **Alternatives rejected:** direct commits to `main` with gates run locally (QuaSaR; rejected: every gate was the agent's own report, and a dependency CVE was first caught at deploy time).

## 5. `docs/PROGRESS.md` is the single state file

- **Date:** 2026-10-07
- **Decision:** Current project state (phase, last step, what is deployed where, next step, open items) lives only in `docs/PROGRESS.md`. Other documents link to it instead of restating it. The `/eng-standard:handoff` skill updates it at the end of every session.
- **Rationale:** Current project state lives in one place; anything else that mentions it points there (constitution X; STANDARD 8.2).
- **Alternatives rejected:** QuaSaR's pattern of a "Last Session" block in `CLAUDE.md`, handoff files, and grep sweeps for stale claims (rejected: state was duplicated across documents and went stale; the sweeps' term lists kept growing).

## 4. New package versions wait 7 days

- **Date:** 2026-10-07
- **Decision:** New package versions aren't installed until they have been public for at least 7 days; security fixes may be exempted by name (STANDARD 5.2). Enforced by pnpm's `minimumReleaseAge: 10080` (minutes) in `templates/pnpm-workspace.yaml`, and, because pnpm 10's frozen install doesn't re-check a lockfile, by the CI check Release age, which reads the registry's publish time of every version a pull request adds to `pnpm-lock.yaml` (added 2026-10-08 after the second Critic pass, R2-8; entry 13).
- **Rationale:** Dependencies are part of the codebase; new versions wait a minimum age before use (constitution IX).
- **Alternatives rejected:** pnpm's 1-day default (rejected: most malicious versions are caught within days, so one day leaves the window open); no delay (rejected: install-time attacks in 2025-26 ran within hours of publication).

## 3. The Critic runs in two forms

- **Date:** 2026-10-07
- **Decision:** A read-only Critic subagent reviews each step's diff against its brief and the spec before the Owner approves the commit, and a cold, separate Critic session reviews each whole phase against the spec. A phase isn't complete until its gate pass is resolved.
- **Rationale:** Nobody grades their own work, and the Critic reviews cold, against the spec, and only reports (constitution II; STANDARD 1.4, 1.5).
- **Alternatives rejected:** phase-gate passes only (rejected: QuaSaR's coverage fell fifteen sessions behind the build); a cold separate-session Critic for every step (rejected: too costly; the per-step subagent is fresh-context already). (foodplan's `docs/SPEC.md` still describes a Critic that runs only at phase gates; that is a foodplan matter for the Planner.)

## 2. Version 1 structure: constitution, standard, enforcement

- **Date:** 2026-10-07
- **Decision:** Three layers. `CONSTITUTION.md` holds the principles, `STANDARD.md` the rules with how each is held ([enforced], [checked], [practice]), and the enforcement is code: `templates/` copied into a project once, and the `eng-standard` plugin, distributed from this repository as a plugin marketplace.
- **Rationale:** A rule that must always hold is enforced by something that can't forget; instruction files hold only what can't be enforced (constitution IV). Exact configuration lives in `templates/` and `plugin/`, and the standard says what must be true (STANDARD, introduction).
- **Alternatives rejected:** a smaller v1 of constitution, templates, and CI, with the plugin later (rejected: hooks are where most QuaSaR rules failed, so they belong in v1).

## 1. The standard lives in its own repository

- **Date:** 2026-10-07
- **Decision:** The constitution, the standard, the templates, and the Claude Code plugin live in their own repository, `engineering-standard`, versioned separately from any project. foodplan is its first consumer.
- **Rationale:** Projects pin a version of the standard and adopt new versions deliberately, reviewing the diff, and the standard changes only through a reviewed change to its own repository (constitution, Amendments; STANDARD, "Changing this standard").
- **Alternatives rejected:** build inside foodplan first and extract later (rejected: the guardrails are generic already and every project needs them from day one); personal `~/.claude` settings only (rejected: not versioned per project, not reviewable, not shareable).
